# Sales Dataset Definition — MVP

## 1. Objective

This document defines the structure and simulation rules of the MVP sales dataset for the Pricing Control Tower project.

This dataset is designed to simulate realistic sales transactions for the MVP of the application. It will be used to:

- populate the transactional table `pct_core.sales_transaction`
- support the analytical layer built during Sprint 3
- enable future KPI calculations
- prepare promotion performance analysis
- provide a credible dataset for demonstration and certification evidence

This document defines the expected grain, fields, generation rules, business assumptions, and known limitations of the simulated sales dataset.

---

## 2. Grain

The grain of the dataset is:

> **1 row = 1 sales transaction line (cash register ticket line)**

A row represents one sold product in one store at one moment in time.

A transaction line can include a quantity greater than 1.

This grain is aligned with the transactional target table `pct_core.sales_transaction`.

---

## 3. Target Structure

The simulated dataset must be directly mappable to the table `pct_core.sales_transaction`.

### Fields

| Field | Type | Required | Description |
|------|------|----------|-------------|
| `transaction_date` | timestamp | yes | Date and time of the transaction |
| `product_id` | integer | yes | Sold product identifier |
| `store_id` | integer | yes | Store identifier where the sale occurred |
| `price_id` | integer | yes | Identifier of the price used for the transaction |
| `promotion_id` | integer | no | Identifier of the promotion applied to the transaction when relevant |
| `quantity` | integer | yes | Quantity sold in the transaction line |
| `unit_price` | numeric(10,2) | yes | Unit price actually paid |
| `revenue` | numeric(12,2) | yes | Revenue of the transaction line (`quantity * unit_price`) |
| `is_promo` | boolean | yes | Indicates whether the transaction is linked to a promotion |
| `price_scope` | varchar(20) | yes | Scope of the price used (`COUNTRY` or `STORE`) |
| `price_type` | varchar(20) | yes | Type of the price used (`STANDARD` or `PROMO`) |

### Important rules

- `transaction_id` is not generated in the dataset file and is handled by the database identity column
- `revenue = quantity * unit_price`
- `is_promo = TRUE` when `promotion_id IS NOT NULL`
- `is_promo = FALSE` when `promotion_id IS NULL`
- `price_scope` and `price_type` must match the selected active price

---

## 4. Target Volume

The target dataset volume for the MVP is:

> **approximately 20,000 rows**

This volume is considered sufficient to:

- test data ingestion
- validate transactional consistency
- produce meaningful analytical aggregations
- simulate promotion effects
- support demonstration during the certification

This target also remains small enough to:

- keep generation logic simple
- allow debugging
- make manual verification possible
- avoid unnecessary complexity for the MVP

---

## 5. Time Period Covered

The simulated dataset must cover:

> **6 months of sales data**

Recommended MVP period:

- `2025-01-01` to `2025-06-30`

This period is long enough to support:

- daily and monthly aggregation
- promotion analysis
- before / during promotion comparisons
- variation across time
- simple seasonality effects

---

## 6. Temporal Generation Rule

Sales are generated **at day level**, with a simple timestamp within the day.

### Rule

For each generated sale:

- the day is selected within the covered period
- the exact transaction timestamp is generated by assigning a simple random time during that day

Example:

- `2025-03-12 14:23:11`
- `2025-05-28 09:41:07`

This approach provides enough temporal realism for the MVP without introducing unnecessary complexity.

---

## 7. Dependencies

The sales dataset generation depends on existing reference data already loaded in the transactional database.

The following tables must be seeded before generating sales:

- `pct_core.product`
- `pct_core.store`
- `pct_core.price`
- `pct_core.promotion`

Without these dependencies, the generated sales dataset cannot be loaded consistently because of:

- foreign key constraints
- pricing logic requirements
- promotion consistency rules

---

## 8. Pricing Logic

Pricing selection is a critical rule of the simulated dataset.

### Business rule

> **Store price has priority over country price**

### Active price rule

A sale must always use a price that is **active at the transaction date**.

The selected `price_id` must therefore be:

- linked to the sold product
- valid on the transaction date
- valid for the relevant pricing scope
- consistent with store-level priority when applicable

### Selection logic

For each simulated sale:

1. identify the product
2. identify the store
3. determine the transaction date
4. search for active prices matching the product and date
5. apply priority:
   - if an active `STORE` price exists for the store, use it
   - otherwise, use the active `COUNTRY` price

### Consequences on output fields

The selected price determines:

- `price_id`
- `unit_price`
- `price_scope`
- `price_type`

These values must remain consistent with each other.

---

## 9. Promotion Logic

The dataset must cover both standard and promotion-driven sales.

### Standard sale

A standard sale follows these rules:

- `promotion_id = NULL`
- `is_promo = FALSE`
- `price_type = STANDARD`

### Promotional sale

A promotional sale follows these rules:

- `promotion_id IS NOT NULL`
- `is_promo = TRUE`
- `price_type = PROMO`

### Promotion validity rule

A promotion can only be used if it is active at the transaction date.

The selected promotion must therefore be consistent with:

- the transaction date
- the applicable product or perimeter
- the store or country scope

### Objective

This logic allows the MVP dataset to support:

- standard performance analysis
- promotion performance analysis
- comparison between promo and non-promo sales

## 10. Minimum Business Cases Covered

The simulated dataset must include the following minimum useful cases for the MVP:

- standard sales
- promotional sales
- multi-day activity
- multi-store activity
- variable quantities
- country price usage
- store price usage
- transactions over the full covered period

These cases are required to make the future analytical layer meaningful.

---

## 11. Simulation Realism Level

The dataset must be realistic enough for the MVP, while staying simple.

### Included in the MVP

The simulation includes:

- variation by product
- variation by store
- promotion effect on sales volume
- light seasonality
- day-level activity variation

### Excluded from the MVP

The simulation does not include:

- customer behavior
- stock constraints
- stock-outs
- basket logic across multiple lines
- advanced cannibalization between products
- advanced elasticity modeling
- complex regional demand behavior

The objective is to create a **credible and usable** dataset, not a fully realistic retail simulation engine.

---

## 12. Simulation Assumptions

The following assumptions are used for the MVP sales simulation.

### Assumption 1 — Independent transaction lines

Each generated transaction line is treated independently.

There is no full ticket structure with multiple products in the same basket in the MVP.

### Assumption 2 — Positive quantities only

Generated quantities are strictly positive.

Typical generated quantities remain small to reflect normal retail behavior.

### Assumption 3 — Revenue is deterministic

Revenue is always calculated as:

`quantity * unit_price`

No additional discounts, taxes, or manual overrides are simulated in the MVP.

### Assumption 4 — Promotions increase sales probability

When a promotion is active, the probability of generating promotional sales increases.

This allows promotion performance indicators to show visible differences.

### Assumption 5 — Light seasonality only

The MVP includes only light seasonality effects, such as:

- slightly higher activity on some days
- moderate day-level variation

No advanced seasonal calendar is simulated.

### Assumption 6 — Price consistency is mandatory

A sale cannot use an arbitrary price.

The chosen price must always be consistent with:

- product
- transaction date
- store / country pricing rule
- price scope priority

---

## 13. Dataset Output Format

The recommended output format for the generated dataset is:

> **CSV**

Recommended file location:

`data/sales_transactions.csv`

### Why CSV

CSV is preferred for the MVP because it is:

- simple to generate
- easy to inspect manually
- easy to load into PostgreSQL
- easy to version and document
- sufficient for the expected volume

---

## 14. Load Readiness

The dataset is considered load-ready if:

- all required fields are present
- data types are compatible with `pct_core.sales_transaction`
- foreign key references are valid
- `revenue` is consistent with `quantity * unit_price`
- `is_promo` is consistent with `promotion_id`
- `price_scope` is valid
- `price_type` is valid

The dataset must therefore be designed for direct loading into the transactional model.

---

## 15. Known Limitations

This MVP dataset has intentionally limited complexity.

### Main limitations

- no customer dimension
- no stock constraints
- no full basket logic
- no taxes or accounting adjustments
- no advanced demand elasticity
- no anomaly injection at this stage

These limitations are acceptable for the MVP because the objective is to support:

- ingestion
- analytics
- KPI calculation
- demonstration of the project architecture

---

## 16. Usage in the Project

This dataset will be used to:

1. generate simulated sales records
2. load sales into `pct_core.sales_transaction`
3. build staging models in dbt
4. create enriched intermediate datasets
5. create sales and promotion marts
6. support future KPI and anomaly analysis

It is therefore a foundational dataset for Sprint 3 and for later analytical and AI-oriented features.

## 18. Summary

The MVP sales dataset is defined as a simulated transactional dataset designed to populate `pct_core.sales_transaction`.

It follows a simple but credible retail logic:

- 1 row = 1 transaction line
- approximately 20,000 rows
- 6 months of activity
- store price priority over country price
- active price required at transaction date
- promotional and non-promotional sales included
- light realism with controlled complexity

This definition provides a stable foundation for dataset generation, loading, and future analytics development.
